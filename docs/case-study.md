# 项目案例：知源 · 企业 AI 知识库

> 一个可溯源的企业知识问答产品，从 MVP 到评测驱动迭代的完整过程。
> 代码与运行方式见 [README](../README.md)。

## 一句话

员工用自然语言提问，AI 只基于企业自己的制度文件作答，每条结论都能点开看到出自哪份文件、哪一页；答不了就明确说不知道，并把「答不上来的问题」自动整理成知识缺口报告，推给负责部门补文档。

---

## 1. 问题：为什么企业不敢直接用 ChatGPT 回答内部问题

| 角色 | 现状 | 核心顾虑 |
|---|---|---|
| 员工 | 制度散落在 PDF、Word、Wiki 里，找不到、找到了也要翻几十页 | 想要快速、准确的答案 |
| 制度负责部门（财务 / HR / 渠道） | 同样的问题每周被问几十遍 | 不想重复回答，又怕员工理解错 |
| 管理者 | 通用大模型会编造公司规则 | **答错一个金额或时限就可能造成损失** |

所以这个产品的核心不是「能回答」，而是 **「可信」**：答案必须来自企业资料、可以溯源、不知道就说不知道。

## 2. 产品定义

**目标用户**：企业内部员工（提问者）、制度负责部门（内容维护者）、AI 产品 / 运营团队（效果负责人）

**核心原则**
1. 只基于知识库作答，不用模型自身知识编造内部规则
2. 每条结论可溯源到文件 / 页码 / 章节
3. 资料不足时明确拒答，而不是猜
4. 效果可量化，每次改动都有数据支撑

**成功指标**

| 层级 | 指标 | 说明 |
|---|---|---|
| 北极星 | 问题解决率 | 已回答且未被点踩的提问占比 |
| 质量 | 答案准确率、引用命中率、误拒率 | 评测集离线度量 |
| 体验 | 首字延迟 | 用户感知速度的关键 |
| 运营 | 拒答率、差评率、知识缺口数 | 线上持续监控，驱动内容补充 |

**MVP 刻意不做的**：权限体系、飞书 / Notion 数据同步、OCR。先把「问 → 答 → 溯源」的核心体验做扎实，再扩展边界。

## 3. 方案

```
上传资料 → 解析（保留页码 / 章节）→ 切片 → 向量化 → 知识库
                                                     ↓
员工提问 → 追问改写 → 混合检索（向量 + BM25）→ 重排 → 拒答闸门 → 大模型生成 → 引用校验 → 带出处的答案
                                                                                    ↓
                                                         点赞 / 点踩 → 知识缺口报告 → 负责部门补文档
                                                                    ↘ 差评转评测题 → 回归测试
```

| 页面 | 解决什么 |
|---|---|
| 知识库管理 | 上传 PDF / Word / Markdown / TXT，看到解析进度和切片结果 |
| AI 问答 | 流式回答 + 引用角标 + 原文查看 + 反馈 |
| 检索详情 | 一次问答的完整轨迹：每一步耗时、召回了什么、分数多少、发给模型的 Prompt |
| RAG 评测 | 26 道带标准答案的评测题，多策略 / 多模型横向对比 |
| 知识洞察 | 拒答率、差评、文档引用排行、知识缺口报告 |

## 4. 关键决策与取舍

### 4.1 「拒答闸门」放在大模型之前

检索结果的相关度不够时，**直接拒答，不调用大模型**。

- 为什么：把「没资料」的问题交给模型，即使 Prompt 要求它拒答，它也有概率编造。从源头不给它编的机会，比事后检查更可靠，还省一次调用费用
- 代价：阈值设高了会误拒。所以阈值不能拍脑袋，必须用数据标定（见 4.4）

### 4.2 引用由后端校验，而不是相信模型

Prompt 要求模型用 `[1] [2]` 标注来源，后端再逐个校验：越界的编号（模型编造的引用）直接删除，剩下的对齐到真实切片。用户看到的每条引用都保证存在。

### 4.3 自己编排 Pipeline，底层用成熟组件

解析、切片、向量库、模型 SDK 都用开源库（pypdf、LangChain text-splitters、Chroma、OpenAI SDK），但没有用 LlamaIndex / LangChain 的完整 RAG 链。

- 为什么：「检索详情」和「评测」需要拿到每一步的中间结果（分数、阈值判断、改写后的问题），框架封装得越深，越难看清、越难调
- 代价：多写了一些编排代码

### 4.4 v0.2：先建评测，再优化检索

v0.1 演示效果不错，但「效果好」只是感觉。于是先建了 26 道题的评测集（直接问法 / 换种问法 / 精确匹配 / 多轮追问 / 应拒答），再逐项加改进、逐项看数据：

| 策略 | 评测通过率 | 误拒率 |
|---|---|---|
| 纯向量检索（v0.1） | 81% | 23% |
| + 追问改写 | 88% | — |
| + BM25 混合检索 | 92% | — |
| + 重排（v0.2） | 100% | 0% |

（仅检索模式逐项叠加；误拒率为完整问答模式的结果）

评测还**推翻了我的一个设计**：第一次加上重排时，误拒率反而从 5% 涨到 14%。查分数分布发现，重排模型对口语化问法打分偏保守（相关切片最低 0.17，而无关切片最高 0.14），初定的 0.2 阈值太高。最终改为「重排分数 ≥ 0.15 **或** 余弦相似度 ≥ 0.55」双信号放行。

### 4.5 v0.3：用评测做模型选型

实际试用时首字常要等 5–8 秒。排查发现默认模型是推理模型，输出前会先内部思考。换模型前先跑评测：

| 模型 | 通过率 | 首字延迟（平均 / 最慢 5%） |
|---|---|---|
| deepseek-flash（推理） | 100% | 2.4 s / 7.5 s |
| deepseek-chat（非推理） | 100% | **0.6 s / 0.7 s** |

质量不变、快 4 倍，于是切换。同时让追问改写只在「像追问」时触发，每轮再省 0.5–2 秒。

**取舍**：评测题偏「查事实」，没有考察复杂推理。如果业务里有大量需要综合推理的问题，应该补题再决定，而不是一刀切。

### 4.6 知识缺口：从「被动回答」到「主动发现盲区」

被拒答和被点踩的问题，本身就是最有价值的需求信号：员工想知道，但文档里没有。知识洞察页把它们按主题归类，给出「该补什么文档、找哪个部门」。

一开始用 Embedding 聚类，效果很差：「有没有班车」和「班车路线」被分成两组。实测发现短问题的向量被「什么时候 / 多少钱」这类句式主导，**同主题的相似度（最低 0.49）可能比跨主题的（最高 0.60）还低**，任何阈值都分不干净。改为由大模型按语义归类后，21 个问题收拢为 10 个清晰主题，天气、未公开战略这类「本就不该回答」的问题也被单独标出。

## 5. 结果

| | v0.1 | v0.3 |
|---|---|---|
| 评测通过率（26 题） | 81% | 100% |
| 答案准确率 | 77% | 100% |
| 误拒率 | 23% | 0% |
| 首字延迟 | 2.4 s（最慢 7.5 s） | 0.6 s（最慢 0.7 s） |
| 能发现知识缺口 | 否 | 是 |

## 6. 局限与诚实说明

- **评测偏乐观**：阈值就是在这 26 道题上标定的，100% 相当于「用考题复习」。可信的结论需要独立的测试集（下一步）
- **数据规模小**：7 份文件、每个主题只有一份，检索很难「找错」；真实企业里，相近主题、新旧版本冲突才是难点
- **判分方式简单**：用关键词判断答案是否正确，会把「九百元」误判为错，也发现不了「答案对但多编了一条」
- **洞察页数据是模拟的**：38 条员工提问和反馈由脚本生成，用于展示效果

## 7. 下一步

1. **评测可信度**：文档扩到约 30 份并加入干扰项（相近主题、新旧版本、长 PDF），评测题扩到约 100 道并拆出独立测试集
2. **回答自检**：生成后检查每句话是否有资料支撑，用「LLM 当评委」补充关键词判分
3. **企业化**：部门权限、飞书 / Notion 同步、知识缺口自动推送给负责人

## 8. 我学到的

- **RAG 的难点不在「能答」，而在「知道自己不知道」**：拒答闸门、引用校验、范围外问题识别，都是在处理这件事
- **没有评测就没有优化**：两次关键决策（重排阈值、模型选型）都被数据推翻或证实了直觉
- **指标要配上可解释性**：评测告诉你「差了多少」，检索详情页告诉你「差在哪一步」，两者缺一不可
- **用户数据是最好的需求来源**：拒答和差评自动变成知识缺口和回归测试，产品才能越用越好
